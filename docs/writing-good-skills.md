# Как писать хорошие скиллы

Конспект приёмов для качественных скиллов Claude Code (по мотивам публичных
практик; сформулировано своими словами).

## Описание — это триггер

`description` — главный сигнал, *когда* подключать скилл. Начинай с условия
запуска: «Use when the user wants to …», и явно добавляй, когда НЕ применять.
Модель видит описания всех скиллов и выбирает по ним.

## Одна ответственность

Скилл решает одну чёткую задачу. Если в названии есть «и» — вероятно, это два
скилла.

## Держи тело компактным

Инструкции — короткие и операционные: шаги, команды, форматы вывода. Тяжёлые
ресурсы (большие справочники, скрипты, схемы) выноси в отдельные файлы внутри
папки скилла и ссылайся на них, чтобы не раздувать контекст.

## Прогрессивное раскрытие

Сначала самое важное (когда и как), детали — ниже или в отдельных файлах.
Скилл должен быстро давать модели «маршрут», а не вываливать всё сразу.

## Проверяй инструменты

Если скилл зависит от внешних утилит — проверь их наличие, предложи установку,
но не ставь без подтверждения.

## Безопасные дефолты

Не выполняй необратимых/внешних действий без подтверждения. Отчёт и план
безопаснее, чем молчаливое применение изменений.

## Чек-лист перед добавлением

- [ ] `name` в kebab-case совпадает с папкой.
- [ ] `description` отвечает на «когда подключать».
- [ ] Тело — операционное, без воды.
- [ ] Нет дублирования с другими скиллами.
- [ ] Запись добавлена в `catalog.json`.
