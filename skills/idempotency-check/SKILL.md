# idempotency-check

## Назначение

Проверка финансовых/критичных операций на идемпотентность и безопасность повторов.

## Почему важно

Сеть ненадёжна: клиент ретраит, вебхук приходит дважды, пользователь жмёт
кнопку дважды. Без идемпотентности → двойное списание/начисление.

## Чек-лист

1. **Idempotency key:** мутирующие операции (платёж, перевод, mint) принимают
   уникальный ключ от клиента; повтор с тем же ключом возвращает прежний
   результат, не выполняя операцию заново.
2. **Хранение результата:** ключ + результат сохранены атомарно с самой операцией
   (одна транзакция), не после.
3. **Уникальное ограничение в БД:** на `idempotency_key` (или `(tx_hash, log_index)`
   для on-chain) — гонка двух параллельных запросов ловится на уровне БД.
4. **Конкурентность:** advisory locks / `SELECT ... FOR UPDATE` / уникальный
   индекс предотвращают двойное выполнение при гонке.
5. **Вебхуки:** обработчики платёжных/on-chain вебхуков идемпотентны (событие
   может прийти несколько раз).

## Паттерн (PostgreSQL)

```sql
-- В одной транзакции:
INSERT INTO operations (idempotency_key, ...) VALUES ($1, ...)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING id;
-- Если RETURNING пуст — операция уже выполнялась, верни сохранённый результат.
```

## На что смотреть

- Повторный вызов API/вебхука создаёт дубль?
- Advisory lock освобождается при ошибке (нет ли leaked lock)?
- Результат и ключ пишутся в одной транзакции?

## Формат вывода

Находки: операция | риск двойного выполнения | как защитить.
